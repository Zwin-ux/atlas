# Decision boundary for the owner and lead

This package is a continuation plan. The graph begins with reconciliation rather than assuming previous proposed changes were silently approved.

## Defaults within the requested direction

Keep the read-only Census app. Prioritize the point-and-ask interaction. Use compact inline and richer fullscreen layouts where supported. Preserve cartographic character while aligning structural UI with current host guidance. Keep public tool names stable. Prefer existing dependencies and a small team. Temporary selection state is per widget, not a saved user account.

The lead can make ordinary implementation choices under these defaults, document their reasons, and continue. It does not need repeated approval for every regression test or CSS adjustment.

## Conflicts to resolve once, in existing authority

- Existing all-height/custom-font design requirements versus mode-aware host-native presentation: record a narrow update in `DESIGN.md`; retain the map's visual character. If the current owner decision differs, preserve it and flag host-guidance compatibility.
- Old challenge priorities versus completing the current ChatGPT app: point the current plan to this bounded release, preserve the frozen challenge artifact, and do not resume competition work.
- Old workflow routing versus current agent instructions: fix the workflow reference, not the product to satisfy stale automation.

Do not interpret a request to “keep going” as permission for a new product category.

## Explicit gates

Real ChatGPT testing may require owner interaction with an authenticated client. Production deployment, release publication, portal verification/submission, credential revocation, paid resources, and external data sharing require their corresponding permissions. A submitted app awaiting review is not an approved app. Missing permissions must remain visible without blocking unrelated local work.

Usability research is a formative quality check, not a claim that eight participants prove demand. Participant availability is tracked independently from implementation completion. Product defects found in testing enter the appropriate existing task; participation counts alone never hide a defect.
