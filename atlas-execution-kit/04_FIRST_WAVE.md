# First working session / get to a real product repair

Do not begin by installing services or generating another comprehensive plan. Start in the current Atlas checkout with the existing agent instructions and this kit's activation prompt.

## What should happen first

The lead establishes repo identity, preserves dirty work, identifies existing active sessions, and reads the current authority/status. It then chooses a narrow integration worktree/base and records ownership in the existing checkpoint. The helper's initial queue deliberately contains only the orientation node.

Once that is accepted, the lead gathers a baseline while an independent QA child prepares source-checked fixtures and the relevant regression cases. These are separate assignments, not two agents both auditing the entire repository. Before relying on native workflows, inspect and minimally correct their stale routing; a verified sequential packet path is an acceptable fallback.

The lead reconciles only the concrete scope/design conflicts from this conversation. Settle the small shared success/refusal and interaction contract. Do not build a new state framework. Then dispatch genuinely independent data and widget repairs with explicit file ownership.

## First visible outcome

Prioritize the smallest confirmed path from a request to a correctly labelled rendered map. The known source-level concerns in the supplied briefs are leads to reproduce, not predetermined bugs that must be patched even if already fixed.

A good first product slice proves at least one real correction or already-correct behavior through a regression test: an ambiguous result cannot become a successful national view; the last correct map remains honestly labelled during a later request; or a named place/explicit level renders the correct geographic identity.

After that proof, continue to selection and the named follow-up instead of doing broad dead-code cleanup. The full product milestone is point-and-ask with a correct recovery state, not “we have an architecture.”

## End-of-slice evidence

Record what changed, actual checks and exit codes, independent review, integrated revision and evidence. Keep active tasks/worktrees, blockers, invalidations and exact next action in the existing status checkpoint. Do not start another status file. The next session resumes the dependency graph rather than repeating discovery.

## Do not mistake these for progress

Changing brands, adding libraries without a need, generating more personas, extending a wiki, expanding coverage, rewriting the renderer, claiming all tests pass from a screenshot, or installing a background retry daemon. None completes the core user journey.
