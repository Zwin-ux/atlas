# Mobile UX + Accessibility Contract (0.78-R)

Status: NAMED DELIVERABLES, folded into the L2a/R feature specs. Program of
record: `.gstack/plan-zoom-band-lod.md`, decisions #29, #31, #35, #36, #38,
#39, #40, #58 (supersedes #33). Covers four things that ride the same DOM
surface and must not be specified independently of each other: the NEAR
product contract, status/state rules, the mobile UX spec, and the
accessibility contract.

## 1. NEAR product contract — NEAR is PLACE INSPECTION, not "more lines"

Per decision #35 (codex-design #1): without this contract, NEAR is "zoom for
zoom's sake." NEAR must be a designed loop with five parts:

- **Entry** — tap a town anchor, or intentional zoom past the NEAR threshold.
- **Reward** — the anchor resolves into recognizable local street structure.
  The selected place stays visually pinned and is never occluded by roads
  during transitions (road z-order yields to the pin, not the reverse).
- **Context** — county orientation persists: the county boundary stays in
  frame, OR a persistent county label substitutes when it does not (see §3
  rim-name fallback).
- **Exit** — one obvious ≥44px "County View" control, plus pinch-out/wheel as
  the gesture-native equivalent.
- **Return** — restores the PRIOR county camera (not a reset to default) and
  keeps the pin. This is decision #29's "zoom-out = exact reverse" applied to
  the drill-down specifically: no motion, layers shed at gesture settle.

This contract also operationalizes the drill-down product metric in
`docs/0.78R_PRODUCT_METRICS.md` — the Entry affordance defined here IS the
metric's definition. A pinch crossing the NEAR threshold without an
intentional Entry gesture is not a drill-down (see that document's accidental
pinch exclusion).

## 2. Status & state rules

Per decision #36 (codex-design #2), non-negotiable baseline:

- **Never blank.** The board is never replaced by empty space while
  something loads.
- **Never a loader.** No spinner, no full-board skeleton, no fade-to-loading
  chrome. The current band stays fully interactive while detail streams in
  behind it.
- **Never a generic toast.** No apology modal, no dismissible snackbar.

One compact status element (banner grammar, same visual language as existing
Atlas banners — not a new component family) sits near the zoom control and
carries exactly these states:

- Loading (detail streaming for the committed band).
- Detail unavailable (persistent while true; a retry is implicitly offered on
  the next gesture, not a manual retry button).
- Degrade (T3's visible-degrade state — storage-down or chunk-fetch failure).

Rules that keep this element honest instead of noisy:

- **Sparse-but-valid is not failure.** A county with genuinely few local
  roads (rural NEAR) renders sparse and honest with **NO status at all** —
  sparse is not routed through the same element as failure, ever.
- **Failed queued drill-down**: if a tap-anchor drill-down cannot resolve
  (pack absent), the camera still completes its move, the board stays at
  MID, and the status element shows "detail unavailable" — the camera
  promise is kept even when the data promise is not.
- **Band changes announce via content, not chrome.** A completed transition
  is legible because the board itself now shows more (or less) — no toast
  saying "now showing MID."

### Transitions are single transactional commits — corrects an internal plan conflict

**Decision #58 supersedes decision #33 and also corrects the Design Pass 2
interaction-state table's own wording ("chunks appear in batches at gesture
settle")** — that phrase describes a visible batch sequence, which #58
explicitly rules out: "batched-visible appearance + atomic swap + visible
ordering cannot coexist... transactional window commits: status shown while
loading, full required chunk set validated, ONE commit. Class priority
governs CONSTRUCTION order only, never a visible batch sequence."

Operative rule for this contract: while a band is loading, the status
element shows "loading" and the CURRENT band stays fully rendered and
interactive. Road-art class-priority (highways before locals, per the Road
Art Contract) governs the order chunks are BUILT off-stage — it is never
observable as roads popping in one class at a time on screen. The instant the
full required chunk set for the incoming band validates, the entire band
appears in one commit. There is no intermediate state where the user watches
partial fabric assemble.

## 3. Mobile UX spec

Named deliverable per decision #38 (codex-design #4) — a perf test cell is
not a responsive-design spec, and gesture ownership is the specific
embedded-widget landmine this section exists to close.

- **One-thumb +/− zoom controls** as the pinch alternative — zoom is never
  pinch-only. Buttons, not a slider (a slider needs two-handed precision on a
  390px-wide surface).
- **One-tap County View return** — the same Exit control from §1, always
  reachable, never buried in a menu.
- **≥44px targets** for every interactive element (zoom controls, County
  View, town anchors) — hit-area inflation applies regardless of the
  element's VISUAL size (decision #26); a town anchor rendered at 12px still
  gets a 44px logical hit box centered on it.
- **Gesture ownership between canvas pan and host page scroll.** Atlas is an
  embedded widget inside the ChatGPT host page, not a full-screen app — a
  one-finger drag on the board must pan the camera, not scroll the host
  conversation, and a host-scroll gesture that begins outside the board must
  not be captured by the canvas. This ownership boundary is tested
  explicitly, not assumed from either surface's default touch handling.
- **Portrait framing at 390×844** is the baseline mobile viewport (matches
  the existing `docs/brain/ROAD_LOT_TERRAIN_CONTACT_GRAMMAR_SPEC.md`
  screenshot convention) — FAR/MID/NEAR composition is authored to read
  correctly in portrait first, landscape second.
- **Safe-area + iframe resize behavior** — controls respect device safe-area
  insets (notch/home-indicator regions) and the board correctly reflows when
  the host iframe resizes (rotation, host chrome show/hide) without a stale
  camera or clipped canvas.
- **Legend placement never covers the selected place.** The per-band scale
  legend (decision #7) has a fixed corner position chosen so it cannot
  overlap the pinned/tapped anchor at any band.
- **Rim-name fallback to a persistent county label.** FAR's county name+state
  lives on the board rim (decision #2); once zoomed past the point where the
  rim leaves the viewport (MID/NEAR), county identity is carried instead by
  a persistent, always-visible county label — orientation is never lost just
  because the rim scrolled off.
- **No hover-only discovery.** Per decision #31 (mouse-parity line): hover
  adds NO chrome beyond a pointer cursor over anchors. Nothing on mobile
  (which has no hover) is ever the only way to discover an interactive
  element that desktop reveals on hover — every affordance is visible
  without a hover state on either surface.
- **Reduced-motion = immediate swaps**, which is also Atlas's DEFAULT motion
  posture given the zero motion budget on transitions (§2, decision #58) —
  `prefers-reduced-motion` does not need a special code path here because the
  default behavior already satisfies it; this line exists so a future
  settle-animation (still deferred, per the Road Art Contract §10) is built
  motion-aware from day one instead of retrofitted.

## 4. Accessibility contract

Named deliverable per decision #39 (codex-design #5) — the canvas is
inherently visual; the accessible surface is the DOM around it.

- **Keyboard-operable zoom + County View, with visible focus states.** The
  one-thumb +/− controls and the County View control from §3 are real
  focusable, keyboard-activatable DOM elements (not canvas-drawn hotspots)
  with a visible focus ring in both themes — keyboard users get the same
  Entry/Exit affordances as touch/mouse users, not a degraded subset.
- **Textual status DOM**, reachable by screen readers, carrying: county name,
  selected place, current detail level (band), and loading/failure state —
  this is the same banner/controls DOM §2's status element already lives in,
  not a second parallel surface. Announcements fire on band-transition
  completion and on entering the degrade state — silence is never the
  screen-reader experience of a state change that a sighted user can see.
- **4.5:1 text contrast in both themes**, extending the existing 12-cell
  contrast audit matrix. Road-class palette entries (Road Art Contract §4)
  are added to that matrix as their own cells — contrast must hold with
  roads present, not only against bare terrain.
- **Non-color class distinction.** Road class is never conveyed by color
  alone — this is the identical rule stated from the Road Art Contract's
  side (`docs/0.78R_ROAD_ART_CONTRACT.md` §4: width/elevation/edge treatment
  first, value second). The two documents must never diverge on this; if
  either changes, the other is reviewed in the same pass.
- **Non-canvas fallback when Pixi cannot initialize.** Follows the existing
  coverage-shell pattern (`web/src/CountyCoverageView.tsx`) — when the
  renderer fails to boot, the user gets a real DOM state describing the
  county and its coverage status, not a blank canvas or a silent failure.
